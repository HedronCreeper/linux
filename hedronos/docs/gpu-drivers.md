# GPUs, drivers, and the first boot that needs no network

The whole difference between "Arch with a nice theme" and HedronOS lives in this file's subject:
what happens between power-on and a working 3D desktop on a machine whose GPU the base install may
not have a driver for yet.

## The database, not a wiki

```
$ hedron-gpu-detect
$ hedron-gpu-detect --json
```

`hedron-gpu-detect` reads `/etc/hedron/gpu-db.json` — a generated file (from this repo's
`tools/gen-gpu-db.py`, built against the kernel tree's own PCI ids and driver Kconfig, with a
sha256 sidecar the verifier checks). Each entry says: vendor, family, the in-kernel driver, whether
that driver is *good enough* for what the user wants, and what package provides the parts that
aren't in-tree. Nothing is a guess: a device that is not in the database is reported as unknown,
and unknown is a status, not a shrug.

Because it is generated from a real kernel tree, when a driver is renamed or removed upstream, the
database loses the entry — and a lost entry is a build failure in `make verify`, not a silent hole
in a user's machine.

## Plans

```
$ hedron-drivers plan
$ hedron-drivers plan
$ hedron-drivers apply --dry-run
$ hedron-drivers apply
```

A *plan* is the answer to "what do I do for this hardware": packages to install, modules to
blacklist, the initramfs hooks to enable, the kernel parameters to set (`nvidia.NVreg_...`,
`amdgpu.sg_display=0`), and the order to do it in. `/etc/hedron/gpu-plans.json` is that answer per
GPU family, generated by `tools/hedron-gpu-plans.py` from `data/driver-rules.toml` and the database,
and baked into the image at build time — which is why an offline install on a machine with an AMD
GPU works: the ISO already contains the packages the plan needs.

`apply` is idempotent and always reports what it *would* do first. Rebinding a GPU (`apply
--rebind`) detaches the driver, replaces it, and re-attaches, which is what you need when a
display-attached card refuses to let go.

## NVIDIA, honestly

The open kernel module (`nvidia-open-dkms`) is the default on Turing and newer. It is not the
default on Pascal and older, because there it does not support the display engine — the plan says
so, and `hedron-drivers plan` prints the reason rather than installing a machine into a black
screen. The three-way choice (proprietary / open / Nouveau) is a decision, so `hedron-drivers
select` exists and its result is remembered in `/var/lib/hedron/drivers/choice`.

When Secure Boot is on and a DKMS module is unsigned, the boot will fail in a way that looks like a
kernel bug. `hedron-doctor scan boot` checks for exactly that, and its fix is a sentence about
`sbctl`/MOK rather than a magic command run as root.

## Boot entries and rollback

`/etc/hedron/boot-entries.toml` describes the menu the firmware shows. The entries are rendered at
install time and re-rendered by a pacman hook on kernel upgrade, which is why "boot with the
fallback driver" is available on the machine that needs it — you cannot use a tool to fix a system
that will not start.

`hedronctl snapshot` and the rollback hook mean a driver change that breaks booting is undone from
the menu, not from a rescue USB stick.

```
$ hedronctl status
$ hedronctl features
```
